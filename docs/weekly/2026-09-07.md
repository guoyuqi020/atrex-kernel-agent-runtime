# 周报：AKA 系统架构、可观测性与自进化实验

## 1. 与宁与师兄讨论 AKA 系统架构

围绕 AKA 的系统边界与责任划分展开讨论，梳理了当前设计中的三个主要问题：Agent 与 Agate / GPU Wiki 的交互记录混在冗长对话中，难以独立追踪；原始服务输出和失败重试过程持续进入上下文，增加 Token 消耗和 Agent 的处理负担；Journal 保存在 Agent 可修改的工作区内，记录不可信，导致外层需要重复评测，且其他过程性观测数据难以事后补采。

据此整理了 Runtime 的设计思路：在 Agent 访问外部服务的必经路径上记录结构化请求与响应，由 Runtime 统一生成面向 Agent 的最小信息视图、处理重试与降级，并将 Journal 从 Agent 工作区独立出来。补充了 AKA 现状、Runtime 交互模型和 Pod / Sidecar 部署草案，明确 Agent 可修改区域、服务代理和外部存储之间的关系。

相关材料：[架构思考（GitHub）](https://github.com/guoyuqi020/atrex-kernel-agent-runtime/blob/main/arch_thinking/README.md)。

## 2. AKA Runtime 组件建设与消融实验

基于上述架构讨论，构建了 AKA Runtime 组件，主要承担两项职责：

- **服务抽象与运行观测**：对 Agate、GPU Wiki 等服务提供统一抽象，强制 Agent 对这些服务的请求经过 Runtime 代理。在代理层记录请求、响应，并与 Agent 的运行状态关联，实现对 Agent 服务使用行为的监控，提升运行过程的可观测性。
- **自动重试与上下文裁剪**：在 Runtime 侧处理服务请求的自动重试，并裁剪服务返回中与当前任务无关的冗余信息，向 Agent 提供精简的结果视图。由此减少故障处理和冗余输出进入 Agent 上下文及被后续请求反复读取的机会，最终降低 Agent 的 Token 消耗。

在此基础上，对 Harness 自进化的设计方案进行了探索，以原始 AKA 为对照，逐步比较以下方案：

- **引入 Runtime 的 AKA 基线（isolated）**：参考原版 AKA 的 Agent 设计，引入 Runtime 代理服务调用、自动处理重试并裁剪返回信息，减少无关冗余信息进入 Agent 上下文。每次优化使用独立 Session，不继承自适应 Agent 状态。
- **多路线竞争（pooled）**：并行探索两条优化路线，在每个 Epoch 结束时选择最佳正确 Kernel，作为下一轮的共同起点。
- **Skills / Tools 继承（retained）**：允许 Agent 在优化过程中积累可复用的技能和工具，并跨 Attempt / Epoch 继承胜出路线的状态。
- **显式自进化（evolve）**：由 Evolver 根据运行历史修改 Prompt、Skills 和 Tools，生成 Challenger，与 Active 竞争后决定是否晋升，同时支持恢复历史 Agent 版本。

在 `fused_moe_fp8`、L20N 环境下，对三种 DSL 分别进行对照实验。括号内为 Latency 变化：isolated-1 对比同一 DSL 的 AKA-1，isolated-2 对比 AKA-2；pooled、retained 与 evolve 对比同一 DSL 的 AKA best-of-two，即两次运行最终 Latency 中的较低值。负值表示降低：

| 方案 | CUDA Latency（μs） | Triton Latency（μs） | CuteDSL Latency（μs） | 总 Token 消耗变化 |
| --- | ---: | ---: | ---: | ---: |
| AKA-1 | 1275.351 | 1105.962 | 1626.643 | — |
| AKA-2 | 1161.882 | 1293.979 | 1205.153 | — |
| isolated-1 | 1662.813（+30.4%） | 1044.369（−5.6%） | 1713.244（+5.3%） | −34.8% |
| isolated-2 | 1517.681（+30.6%） | 1058.530（−18.2%） | 1309.905（+8.7%） | −34.7% |
| pooled | 1086.325（−6.5%） | 1096.040（−0.9%） | 1365.019（+13.3%） | −39.2% |
| retained | 1199.896（+3.3%） | 1138.217（+2.9%） | 1126.074（−6.6%） | −41.8% |
| evolve | 1295.646（+11.5%） | 1084.768（−1.9%） | 1391.772（+15.5%） | −43.6% |

初步分析：

1. **引入 Runtime 后，Token 消耗显著降低，但可能对优化能力存在负面影响。** 两次 isolated 相对对应的 AKA 运行，Token 消耗分别降低 34.8% 和 34.7%，但 CUDA 和 CuteDSL 的 Latency 均上升。仍需仔细排查流程调整、信息裁剪等因素是否影响了 Agent 的优化能力，并通过更多独立实验排除优化偶然性的影响。
2. **多路线竞争带来部分 DSL 的性能收益，但仍存在 DSL 差异。** pooled 并行运行两条优化路线，定期取较优 Kernel 广播为下一轮共同起点。对比 AKA best-of-two，CUDA 和 Triton 的 Latency 降低，CuteDSL 则上升；相比 isolated 平均值，CUDA 和 CuteDSL 改善，但 Triton 尚未改善。其总 Token 消耗也低于两次 isolated 的合计用量。这一方向值得继续推进，但收益的稳定性仍需更多重复实验验证。
3. **当前自进化方案主要体现为 Token 效率改善，对优化能力的影响则以负面为主。** 无论是总结、继承 Skills / Tools（retained），还是显式 meta-evolve（evolve），相对 pooled 都进一步降低了 Token 消耗，但各自在三个 DSL 中有两个的 Latency 上升。也存在 retained 改善 CuteDSL、evolve 改善 Triton 的例外，尚不能认定自进化普遍有害。后续需要进一步分析具体的 Agent 改动及其影响，并通过更多实验排除偶然性。

## 3. 基于 Runtime 可观测系统发现并修复 Agate Gateway Bug

基于 AKA Runtime 可观测系统的反馈，在检查 Agent 与 Agate 的交互记录时，发现 Agate Profile 任务的错误响应存在冗余转义字符过多、错误信息难以阅读的 Bug。随后完成修复，改善错误输出的可读性，便于 Agent 和开发者定位故障。关联 [Issue #702283](https://code.alibaba-inc.com/tre-infra/atrex-gpu-gateway/issues#openWorkitem=702283)，已于 8 月 31 日标记为 Fixed，目前状态为已完成。

排查过程中还反馈了错误阶段归类问题：correctness 阶段失败时，compile 阶段也会出现同一条正确性错误信息，容易误导故障定位；这一点作为补充问题反馈，暂不计入已确认修复的范围。

## 4. 向御元反馈 AKA 对 Agate 的实际需求与接口差异

基于 Runtime 可观测系统记录的 Agent–Agate 交互，向御元反馈 AKA 的实际评测需求与现有接口之间的差异，重点包括：

- **ABBA 测试**：对候选 Kernel 与基线进行 ABBA 配对性能测量，降低测量波动对比较结果的影响。
- **算子自定义输入测试**：支持使用自定义输入和 Shape 测试算子，满足 Agent 优化过程中的探索与验证需求。
- **独立正确性测试**：只检查计算结果是否正确，不运行性能测量，便于快速验证候选 Kernel。
