## 统计口径

- **本轮结束时保留延迟**：初始值来自 `memory/v0.json`；只有 `accepted=true` 才更新为 Supervisor 验收的 `verification.candidate_latency_us`。其他轮次沿用上一次晋升的数值，**不代表每轮重新测得相同延迟**。
- **候选终评延迟**：另列本轮权威终评的候选值；即使比保留值小，也可能未过当轮对照测量的 1% 晋升门槛。它不能直接视为已获得的优化。延迟使用原验收记录的几何平均口径，不混入 Agent 自测最佳值或后续 SOTA 对照实验。
- **Token**：取每轮 `telemetry.summary.json → phase_tokens.terminal_usage`，`total_tokens = input_tokens + output_tokens`。这里 input **已经包含缓存读写**，不再加一次 cache。每次模型请求处理同一历史上下文所产生的 cache-read 属于该次请求的用量，并非同一条账目重复相加。M = 1,000,000 tokens。
- **本轮耗时（近似 wall-clock）**：从归档 `BRIEF.md` 的原始修改时间，到 outcome / promotion Git Commit 的提交时间。全部 96 轮的结束时间均与 `attempt.json` 修改时间相差不超过 1 秒。该口径包含 Agate 等待、终评和轮内恢复，不是模型净推理时间；不包含轮次间停机和 EP1 之前的初始化。开始时间由文件时间恢复，不能当作原生进程计时精度。EP1 的耗时还包含中断后的收尾登记。
- **缺失不记零**：`†` 表示归档 usage 为 partial；“缺失”表示没有可用用量。EP77 起累计只代表已知部分。没有把 phase 分类不完整误判为整个 terminal usage 缺失。

3. **usage 缺失**：EP77、EP78、EP79、EP80、EP81、EP82、EP83、EP88、EP90、EP91、EP92、EP93、EP94、EP95。尽管控制器的 `tokens` 可能是 0，终态 usage 为 null / unavailable，故显示“缺失”。
4. **恢复没有重复加累计快照**：EP3 有 2 次 invocation、EP30 有 3 次。核对了所有可用的 invocation 用量之和与 Episode terminal usage 一致；原 Codex 账本实现按增量读取，跳过相同 cumulative usage，fallback 对恢复前后的 session 总量作差。本报告只加一次 Episode 汇总，不再叠加 invocation、phase 和 orchestration 等重复视图。这里的核对基于归档摘要和采集代码，**不是重新核对供应商实际扣费**。
5. **不同轮次的对照测量会波动**：例如 EP21 对照 incumbent 的终评值不是 EP20 晋升时保存值。保留延迟曲线按晋升时值记录；未通过晋升的候选不能据此跨轮替换保留值。
6. **原始报告有截断时间差**：复现包中的实验报告描述到 EP76，而 `state.json` 已到 EP96。本报告以逐轮归档和状态表为准，EP97 明确标为未完成。
